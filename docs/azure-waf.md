# Azure WAF：HTTP応答とログ取り込みを分けて確認する

対象期間: 2026-10-26〜27 · 公開日: 2026-10-31 · 種別: 作業記録

## 構成と目的

Application Gateway WAF_v2、バックエンドVM 2台、WAFポリシー、Front Door経路、Log Analyticsの診断設定を組み合わせ、検証リクエストとログの関係を確認した。実環境名・公開IP・エンドポイント名は省略した。

## 観測・設定変更の記録

| 項目 | 記録 | 判断できる範囲 |
|---|---|---|
| WAFポリシー | DetectionからPreventionへ変更 | ブロック動作を試す構成 |
| 診断設定 | リソース固有テーブル、ログ・メトリクス送信を設定 | 設定と取り込み成功は別 |
| 検証入力 | 正常アクセスとSQLi相当の入力を送信 | バックエンド侵害の成立は意味しない |
| HTTP応答 | 403 / 502、Front Door経由で200 / 403を観測した記録 | 応答だけで拒否主体・ルールIDは断定できない |
| 日次クォータ | 0.05GB/日でOverQuota、1.0GB/日へ設定変更 | リセット・反映後の回復確認は別に必要 |
| 経路反映 | Front Door反映を待って再確認 | 当時は約30分程度。保証時間ではない |
| Firewallログ | 初回未出力・取り込み遅延の切り分けが課題 | この資料だけで出力完了とはしない |

## 切り分けの順序

1. 正常リクエストで経路とバックエンドが応答するか。
2. 同じ経路で検証入力の応答が変わるか。
3. Accessログに対象時刻の記録があるか。
4. FirewallログのAction・RuleId・関連IDと突合できるか。
5. クォータ、診断設定、検索期間、取り込み遅延を確認する。

403はWAF以外でも返せる。502も経路、プローブ、Hostヘッダー、バックエンド応答等で発生し得る。「403が返ったのでWAFのSQLi検知成功」と単独では結論づけない。

## ログ存在確認のKQL例

以下は追加確認に使う例であり、今回Azure上に実行した結果ではない。

実行:

```kusto
AGWAccessLogs
| where TimeGenerated > ago(1h)
| take 20
```

確認:

```kusto
AGWFirewallLogs
| where TimeGenerated > ago(1h)
| summarize Rows=count(), Latest=max(TimeGenerated)
```

テーブルがないエラーと、テーブルはあるが0行という結果を分ける。旧形式の`AzureDiagnostics`を使う場合は送信形式に合わせる。Application GatewayとFront Doorのログも同一視しない。

## 学び

HTTP応答、ログ収集、分析ルールの評価、通知は別の段階である。この公開記録は主に応答と設定変更までを示す。今後は同じRun ID・時刻でAccess / Firewallログとアラートを結びつけ、どこまで成立したかを説明できる証跡を追加する。
