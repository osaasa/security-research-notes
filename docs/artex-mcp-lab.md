# ARTEX：既存コードの改修とMCP検証

公開日: 2026-10-31 · 種別: ソース確認 / 作業記録 / 設計

## 目的と担当範囲

既存のARTEXをDockerで動かし、AIと外部ツールを接続する仕組みを理解する。環境構築、コードの読み解き、改修・検証の整理にChatGPT / Codexを活用した。

ARTEX本体は第三者の既存プロジェクトであり、私がゼロから開発したものではない。本記事では、管理している作業用リポジトリで確認できた変更と、ローカルでの検証記録を整理する。上流の基本機能を自分の新規開発として扱わない。

## ソースで確認した変更

作業用リポジトリのコミット`837cbbf9cfaebdf088b2c32490b7f9b920781316`を確認した。タイトルは「Backport OpenAI Responses API to ARTEX v0.2.0 and add local Compose setup」。この公開版には既存ソース一式を転載していない。

テストには`httptest`による応答を使う。要求形式やツール呼び出しの解析を確認する設計であり、実APIの接続成功や実モデルの性能を証明するものではない。この公開作業ではGoテスト・Dockerビルド・有料API接続を再実行していない。

## Docker / MCPの作業記録

Windows / PowerShellとDockerを使用し、`run_recon → http_check → analyze_results`を試した。Juice Shopを対象とする作業記録には、バージョン`20.2.0`の確認と`report_ja.md`出力が残る。この版にはレポート原本とHTTP証跡一式を添付していないため、個別の脆弱性が成立したとは主張しない。

別段階の試作には`synthetic-fixture`やMock分析もある。これを実機の結果と合算しない。ローカルHTTP応答がある場合も、接続成功と脆弱性の成立を分ける。

## 学んだこと

MCPの呼び出し経路に加え、計画、状態管理、評価、再試行を別に設計する必要がある。UIで選択できること、DBへ保存できること、要求を送れること、実行結果を正しく判定できることを分けて確認する観点が役立った。

各実行では、Run ID、ツール名、引数、開始・終了時刻、実通信の有無、応答、例外、結果ファイルのハッシュを残す。LLMが「成功」と説明しても、実行証跡を確認して判定する。

## 次の検証

ローカル演習環境の最小シナリオを固定し、HTTP証跡・レポート・Sentinelログを同じRun IDと時刻で照合する。検知遅延は実イベント時刻とアラート時刻の差で測り、レポート生成完了を検知成功に数えない。
